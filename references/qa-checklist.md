# 交付前自检

**目标：把「用户看图 → 说不对 → 我改」压缩掉。**

用户真正该介入的只有两件事：文案取舍、审美拍板。其余问题都是我自己该发现的 ——
孤字、方块字形、素材过大、分类配色没用上，靠肉眼来回三轮纯属浪费。

分两层：**能量的交给脚本，量不出的按清单自查。**

---

## 第一层：脚本自检

```bash
python scripts/render_xhs.py content.md -t <theme> --dry-run
```

自动检查（每一条都对应一次真实踩过的坑）：

| 检查 | 触发条件 | 由来 |
|---|---|---|
| 卡片溢出 | 渲染高度 > 画布高度 | 组件比纯文本容易溢出 |
| 卡片偏空 | 内容不足画布高度 62% | 探针报"平均亮度低于样图"多半就是这个。**62% 只是及格线，不是好看线**——实测多张卡片踩着 70-80% 通过检查、肉眼仍然一眼看出底部大片空白（kraft-marker 那次真实案例），**dry-run 无警告不等于不用再看一眼**，尤其是"分离卡"模式（每卡独立画布，不像瀑布流会自然被裁掉空白）|
| 封面字数 | 标题最长行 >15 / 副标题 >15 | 副标题无自动缩放，超了直接溢出 |
| **封面孤字** | 标题末行宽度 < 首行 25% | 上游 bug：字号只按字数查表，不校验放不放得下 |
| **缺字形** | 标题含 `①②` `Ⅰ` `㊙` `🆚` 等 | 中文展示字体字符集不全，渲染成空心方块 |
| **分类配色未用** | 主题有 `palette` 但版式无 `.palette` | 「生成的图很单调」最常见的直接原因 |
| **封面硬塞** | 封面同时有栅格和配图 | 空间只够一样，两样都放会挤 |
| 素材缺失 | 引用的文件找不到 | |

带样图时追加客观差距：

```bash
python scripts/render_xhs.py content.md -t <theme> --dry-run --sample sample.png
```

会输出平均亮度、明暗对比、饱和分布、色板距离五项差值。
**先修完上面的硬错误再看这些** —— 硬错误没清完，"像不像"没有讨论价值。

`--dry-run` 发现问题时退出码为 1。

## 第二层：脚本量不出的，我自己看

出图后逐张过一遍。这些是探针量不出、但直接决定成品好坏的：

### 版式

- [ ] 并列内容是否用了栅格，而不是堆成一列 bullet
- [ ] 一张卡是不是只讲一件事
- [ ] 同一行的面板高度是否一致（`vs` 要 `align-items: stretch`）
- [ ] 浮动素材后面的标题有没有被裹进去
- [ ] 多栏里的中文有没有压字（栏越窄，文案越要短）
- [ ] **每张卡的内容是否接近铺满画布，而不是只信 dry-run 通过**——底部有明显大片
      背景色/纹理裸露就是偏空，加内容（例句标签、小结栅格、多一个配图）而不是
      硬加 padding：canvas 高度固定，padding 不会让视觉上"填满"，只有真实元素
      会。同一批卡里最"轻"的收尾卡最容易漏——可以往回呼应开头的分类栅格当收尾，
      既加密度又能形成首尾呼应
- [ ] **标签/贴纸类小组件（`.tag`/`.sticker`/`.cap`）的字体是否跟标题字体一致**
      ——两者默认可能分别继承正文字体和标题字体，同一张卡里粗体标题旁边站着
      细体标签，对比会很扎眼，尤其是标题字体本身个性强（手绘/marker 类主题）时

### 文字

- [ ] 封面标题断行位置是否自然（用 `<br>` 手动控制比自动断好）
- [ ] emoji 是否都是彩色 —— 部分 emoji（🆚 等）有文字形态回退，会被中文标题字体接管成单色描边
- [ ] 有没有孤立的标点或单字挂在行尾

### 颜色

- [ ] 分类色是否**并列使用**（每栏一色），而不是全卡一个色
- [ ] 深色主题上的分类色够不够亮（渲染器会自动生成提亮版，但样图取色偏暗时仍需检查）
- [ ] 强调色出现频率是否过高 —— 满屏强调等于没有强调

### 素材

- [ ] 去背 PNG 是否保留了透明（不该出现黑底或白框）——**注意 fetch_images.py 的
      "透明检测"可能被骗**：有些图库素材看着背景透明，实际是纯色深底直接画进了
      像素（alpha 通道处处 255），只有真的抽样查 `im.getpixel()` 的 alpha 值
      才能确认，不能只信文件名带 `vector` 或联系表看着像透明
- [ ] 素材是否在辅助表意 —— 去掉它信息量会不会下降？不会就删
- [ ] 图片是否被压到合适尺寸（`--dry-run` 不报这个，但 HTML 过大会拖慢渲染）

### 细节效果

- [ ] 加了描边（`-webkit-text-stroke`）、纹理底纹这类细节效果后，**不要只看整卡
      缩略图判断"有没有生效"**——缩放到手机屏幕大小时几像素的描边基本看不出来，
      容易误判"没生效"又去调大参数。用 PIL/截图裁出标题局部区域放大看，才能
      确认效果真的画出来了

## 什么时候必须问用户

只有这三类，其余自己决断：

1. **文案改动幅度大** —— 尤其封面标题。原标题是用户的声音，换掉要说明理由并给回退选项。
2. **需要新增内容** —— 缺结尾行动卡、竞品对比缺具体数据。我不替用户编。
3. **风格方向的取舍** —— 比如"四张卡全用实色块统一，还是留一张重点卡 + 三张轻量卡"。
   这是审美判断，没有对错。

**没有对错的取舍，优先出两版让用户挑，而不是问。** 封面的宫格 vs 配图就是典型 ——
`<!-- or -->` 分隔封面正文即可出 `cover-a` / `cover-b`。一次渲染的成本远低于
一轮来回问答。

**不要为下面这些去问用户**：溢出怎么办、字形方块怎么改、素材太大、要不要用分类配色。
这些都有确定答案，自己修完在交付说明里写一句即可。

---

## 交付时说什么

- 改动了用户文案的地方，逐条列「原文 → 改后 → 原因」
- 自己修掉的技术问题，一句话带过即可，不要展开
- 剩下的已知差距要**主动说**，不要等用户发现 —— 例如"内容密度低于样图，因为原文每节只有一句话"
- 用到需授权字体时必须提示
